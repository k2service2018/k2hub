# Expense Claim Web App (Google Apps Script)

เว็บแอปกรอกใบเบิกค่าใช้จ่ายตามแบบฟอร์ม **FIN-2026-EXP-001.00** พร้อมระบบสมาชิกของตัวเอง
สายอนุมัติ 2 ขั้น (Admin ตรวจสอบ → Manager อนุมัติ) และการพิมพ์เอกสารเป็น PDF

ระบบสมาชิกยกโครงมาจาก **K2 Tender Price** (`AuthService.gs`) ทั้งชุด —
สมัคร/ล็อกอินด้วยอีเมลกับรหัสผ่านของระบบเอง **ไม่ผูกกับบัญชี Google**
จึง deploy แบบเปิดให้ใครก็เข้าใช้ได้

หน้าจอรองรับ **2 ภาษา (ไทย / English)** และ **โหมดสว่าง–มืด**
ใช้ชุดสี ฟอนต์ ไอคอน และกล่องแจ้งเตือนเดียวกับ K2 Tender Price
(Plus Jakarta Sans + Noto Sans Thai · Lucide Icons · SweetAlert2)

การยืนยัน แจ้งเตือน และแจ้ง error ทุกจุดใช้ SweetAlert2 ปรับสีตามธีมที่เลือกอยู่
ถ้า CDN โหลดไม่ขึ้น ระบบจะถอยไปใช้กล่อง modal และ toast ของตัวเองอัตโนมัติ ไม่ค้าง

## Secrets.gs — ค่าที่ไม่ถูกเก็บใน git

repo `k2hub` เป็น **public** ค่าที่ระบุตัวตนของที่ติดตั้งจริงจึงไม่ถูก commit ทั้งหมดอยู่ในไฟล์เดียวคือ `Secrets.gs`
ซึ่ง `.gitignore` กันไว้ แต่ `.claspignore` **ไม่ได้** กัน — `clasp push` จึงยังส่งขึ้นโปรเจกต์จริงตามปกติ

คัดลอก `Secrets.example.gs` เป็น `Secrets.gs` แล้วเติมค่า

| คีย์ | ค่า |
|---|---|
| `SPREADSHEET_ID` | ID ของ Expense_Claim_DB |
| `SUPER_ADMIN_EMAIL` | อีเมลผู้ดูแลระบบคนแรก |
| `SEED_PASSWORD` | รหัสผ่านตั้งต้นของบัญชีนั้น เปลี่ยนทันทีหลังเข้าระบบครั้งแรก |
| `PDF_FOLDER_ID` | โฟลเดอร์เก็บ PDF เว้นว่างได้ = My Drive |
| `WEBAPP_URL` | URL ของ deployment ใช้ทำลิงก์ในอีเมลแจ้งเตือน เว้นว่างได้ |

`.clasp.json` ก็ถูกกันไว้ด้วยเพราะมี `scriptId` กับ `parentId` คัดลอกจาก `.clasp.json.example` แล้วเติมเอง

โค้ดอ่านค่าผ่าน `secret_('KEY')` ใน `Config.gs` ซึ่งลอง `SECRETS` ก่อน แล้วค่อยตกไปที่ Script Properties
ถ้าไม่อยากวางไฟล์บนเครื่อง ตั้งใน **Project Settings → Script Properties** ด้วยชื่อคีย์เดียวกันก็ได้เหมือนกัน

`setup()` จะเตือนท้ายข้อความถ้าคีย์จำเป็นยังว่างอยู่

## ขั้นตอนติดตั้ง

### 1. ฐานข้อมูล

สร้างไว้แล้วในบัญชีของทีม วางล้อโครงสร้างเดียวกับ K2Tender

```
My Drive / WebApp / ExpenseClaim / Expense_Claim_DB     ← ของใหม่
My Drive / WebApp / K2Tender     / Tender_Price_Webapp_DB
```

ID ของชีตอยู่ใน `Secrets.gs` ไม่ได้อยู่ใน repo จึงใช้ได้ทั้งแบบผูกกับชีตและแบบ standalone

### 2. สร้างโปรเจกต์สคริปต์

1. เปิด `Expense_Claim_DB` → เมนู **Extensions → Apps Script**
2. ลบไฟล์ `Code.gs` ที่มีมาให้ แล้วสร้างไฟล์ตามรายการข้างบนทีละไฟล์
   - ไฟล์ `.gs` → **Files → + → Script** (ตั้งชื่อโดยไม่ต้องใส่ `.gs`)
   - ไฟล์ `.html` → **Files → + → HTML** (ตั้งชื่อโดยไม่ต้องใส่ `.html`)
3. เปิด `appsscript.json` ให้เห็น: **Project Settings → ☑ Show "appsscript.json" manifest file**
   แล้ววางเนื้อหาทับ

> ถ้าใช้ [clasp](https://github.com/google/clasp): `clasp login` ด้วยบัญชีเจ้าของโปรเจกต์
> แล้ว `clasp clone <script id>` และ `clasp push` จากโฟลเดอร์นี้

### 3. ตั้งค่า

บัญชีผู้ดูแลตั้งต้นและ ID ของชีตอยู่ใน `Secrets.gs` ตามหัวข้อข้างบน ส่วนที่เหลือแก้ใน `Config.gs`

```javascript
FINANCE_EMAILS: ['finance@company.com'],
COMPANY: 'ชื่อบริษัทของคุณ',
AUTO_APPROVE_REGISTRATION: true,
```

`AUTO_APPROVE_REGISTRATION: false` = ต้องรอผู้ดูแลเปิดใช้งานบัญชีก่อนเข้าระบบได้

### 4. สร้างชีตข้อมูล

รันฟังก์ชัน `setup` หนึ่งครั้งจาก editor (เลือก `setup` → **Run**) หรือใช้เมนู
**Expense Claim → Setup ชีตข้อมูล** ในตัว Spreadsheet

จะได้ชีต: `Claims`, `ClaimItems`, `Users`, `ApprovalLog`, `Master`
พร้อมบัญชีผู้ดูแลตั้งต้นตาม `SUPER_ADMIN_EMAIL` / `SEED_PASSWORD`

> ถ้ามีชีต `Users` จาก Tender อยู่แล้ว `setup` จะ **เติมคอลัมน์ที่ขาดต่อท้าย** โดยไม่ลบข้อมูลเดิม —
> ผู้ใช้และรหัสผ่านเดิมใช้ล็อกอินได้ทันที เหลือแค่กรอกแผนก/ตำแหน่ง/ผู้อนุมัติในหน้าโปรไฟล์

### 5. Deploy เป็นเว็บแอป

**Deploy → New deployment → Web app**

| ตัวเลือก | ค่าที่ต้องเลือก |
|---|---|
| Execute as | **Me** — สคริปต์เข้าถึงชีตและส่งอีเมลด้วยบัญชีคุณ |
| Who has access | **Anyone** — ใครมีลิงก์ก็เข้าใช้ได้ |

คัดลอก URL ที่ได้ไปแจกให้พนักงาน

> การยืนยันตัวตนทำในตัวแอปเอง (อีเมล + รหัสผ่าน) ไม่ได้พึ่ง Google Sign-in
> "Anyone" จึงหมายถึงเข้าถึง **หน้า Login** ได้เท่านั้น ไม่ใช่เข้าถึงข้อมูล

### 6. เข้าใช้ครั้งแรก

1. เปิด URL → ล็อกอินด้วย `SUPER_ADMIN_EMAIL` / `SEED_PASSWORD`
2. ไปแท็บ **โปรไฟล์ → เปลี่ยนรหัสผ่าน** เปลี่ยนทันที
3. พนักงานกด **สมัครสมาชิก** ด้วยอีเมลอะไรก็ได้ (ได้บทบาท `Sale` เสมอ)
4. ผู้ดูแลไปแท็บ **จัดการผู้ใช้** เพื่อตั้งบทบาทให้ผู้ตรวจสอบและผู้อนุมัติ

| บทบาท | ทำอะไรได้ |
|---|---|
| `Sale` | จัดทำและส่งใบเบิกของตัวเอง (ค่าเริ่มต้นของผู้สมัครใหม่) |
| `Admin` | **ตรวจสอบรายการ** ของผู้อื่น แก้ไขหรือตีกลับได้ |
| `Manager` | อนุมัติขั้นสุดท้าย ตีกลับได้ |
| `Finance` | เห็นทุกใบ บันทึกการจ่ายเงิน |
| `Super Admin` | จัดการผู้ใช้และสิทธิ์ทั้งหมด |

ชื่อบทบาทตรงกับ Tender ทุกตัว ยกเว้นที่ Tender มี `RA&SCM` เพิ่ม

## ระบบสมาชิก

| ส่วน | รายละเอียด |
|---|---|
| รหัสผ่าน | salted SHA-256 วนซ้ำ 5,000 รอบ ไม่เคยเก็บเป็นข้อความธรรมดา |
| เทียบรหัสผ่าน | เทียบแบบ constant-time และ hash ทิ้งหนึ่งครั้งเมื่อไม่พบอีเมล เพื่อไม่ให้เดาได้ว่าอีเมลไหนมีบัญชี |
| Session | token สุ่มเก็บใน `ScriptProperties` หมดอายุแบบนับจากการใช้งานล่าสุด 2 ชม. |
| ฝั่งเบราว์เซอร์ | เก็บ token ใน `localStorage` และแนบไปกับทุกคำเรียกเซิร์ฟเวอร์ |
| ลืมรหัสผ่าน | ส่งลิงก์ `?reset=<token>` ทางอีเมล อายุ 30 นาที |
| เปลี่ยนรหัสผ่าน | ทุกเส้นทาง (เปลี่ยนเอง / ลิงก์รีเซ็ต / ผู้ดูแลตั้งให้) จะปิด session เดิมทุกเครื่อง |

ปรับอายุ session ได้ที่ `CFG.SESSION` และความยาวรหัสผ่านขั้นต่ำที่ `CFG.MIN_PASSWORD_LEN`

## หน้าจอในระบบ

| หน้า | ใครใช้ | ทำอะไร |
|---|---|---|
| **เข้าสู่ระบบ / สมัครสมาชิก** | ทุกคน | ล็อกอิน สมัคร ลืมรหัสผ่าน ตั้งรหัสผ่านใหม่จากลิงก์ |
| **แบบฟอร์ม** | ทุกคน | กรอกใบเบิกรวมสูงสุด 25 บรรทัด แยกเป็น 2 ตาราง: **รายการค่าใช้จ่าย** (เลือกประเภท + จำนวนเงิน) และ **ค่าน้ำมัน — Fleet Card** (ลิตร + จำนวนเงิน) ระบบกระจายยอดลงคอลัมน์ G–S ให้เอง |
| **ใบเบิกของฉัน** | ทุกคน | ค้นหา เปิด แก้ไข ลบฉบับร่าง |
| **รอฉันดำเนินการ** | Admin / Manager / Finance | ใบที่รอคุณดำเนินการ พร้อมตัวนับแยกตามขั้น — หน้าเดียวใช้ได้ทุกบทบาท แสดงเฉพาะงานที่ตรงกับสิทธิ์ของคุณ |
| **ตรวจสอบรายการ** | Admin / Manager | ตรวจทีละบรรทัด ติดธง ผ่าน/ติดปัญหา ใส่หมายเหตุ แก้ตัวเลข |
| **จัดการผู้ใช้** | Super Admin | เปิด/ปิดบัญชี ตั้งบทบาท ตั้งรหัสผ่านให้ผู้ใช้ |
| **โปรไฟล์** | ทุกคน | แก้ข้อมูลตัวเอง และเปลี่ยนรหัสผ่าน |

ปุ่มสลับภาษา (🌐 EN / ไทย) และปุ่มสลับโหมดสว่าง–มืด อยู่มุมขวาบนของทุกหน้า
ระบบจำค่าที่เลือกไว้ใน `localStorage` ของเบราว์เซอร์

> อีเมล **ผู้ตรวจสอบ (Admin)** และ **ผู้อนุมัติ (Manager)** ไม่มีให้กรอกในหน้าไหนของผู้ใช้ทั่วไปแล้ว
> ระบบเลือกผู้รับให้เองตามลำดับนี้: ค่าที่ Super Admin ตั้งไว้ให้ผู้ใช้ในหน้า **จัดการผู้ใช้** →
> ถ้าไม่ได้ตั้ง จะส่งให้ **ผู้ใช้บทบาทนั้นทุกคน** ช่วยกันรับ (ยกเว้นตัวผู้จัดทำเอง)

### ค่าน้ำมัน — Fleet Card

ค่าน้ำมันจ่ายผ่าน fleet card จึงแยกเป็นตารางของตัวเอง และ**ไม่นับรวมในยอดที่ขอเบิก**
แต่ยังต้องบันทึกจำนวนลิตรและจำนวนเงิน — ข้อมูลลงคอลัมน์ `F` (Liter) และ `G` (Gasoline) ของแบบฟอร์ม Excel ตามเดิม
คอลัมน์ **Total** ของแต่ละบรรทัดและยอดรวมทั้งใบคิดจาก `H:S` เท่านั้น ไม่รวม `G`

ถ้าต้องการให้ค่าน้ำมันกลับมานับเป็นเงินเบิก ให้ลบ `fleetCard: true` ออกจากฟิลด์ `gasoline` ใน `Config.gs`

### หน้าแรกหลังเข้าสู่ระบบ

หน้าแรกยึดตาม**บทบาท** ไม่ได้ยึดตามว่ามีงานค้างหรือไม่:

- `Super Admin` → **ใบเบิกทั้งหมด** (หน้าเดียวกับ ใบเบิกของฉัน แต่เห็นทุกใบในระบบ)
- `Admin` / `Manager` / `Finance` → **รอฉันดำเนินการ** เสมอ ถึงคิวจะว่างก็ตาม
- `Sale` → **แบบฟอร์ม** พร้อมใบใหม่ให้กรอก

### Super Admin เห็นทุกอย่าง ทำแทนได้ทุกอย่าง แต่ไม่มีคิวงานของตัวเอง

แยก **อำนาจ** ออกจาก **คิวงาน** เป็นคนละเรื่อง:

| | ใช้ตัดสินว่า | Super Admin |
|---|---|---|
| `isChecker` / `isApprover` / `isFinance` | เปิดใบไหนได้ กดปุ่มไหนได้ | จริงเสมอ — ทำแทนได้ทุกขั้น |
| `checkerDuty` / `approverDuty` / `financeDuty` | ใบไหนเข้าคิว **รอฉันดำเนินการ** | เท็จ เว้นแต่ถือบทบาทนั้นจริง |

`queueCheck_` / `queueApprove_` / `queuePay_` ใน `Approval.gs` เป็นตัวตัดสินคิว ส่วน
`canCheck` / `canApprove` / `canPay` เป็นตัวตัดสินปุ่ม ทั้งสองชุดอยู่ใน `claimPermissions_` เหมือนกัน

**กันตรวจใบตัวเอง** ทุกบทบาทรวมถึง Super Admin — เดิม `canCheckClaim_` คืน `true` ให้ Super Admin
ก่อนจะถึงบรรทัดที่กันไว้ ทำให้ Super Admin ถูกขอให้ตรวจใบที่ตัวเองเป็นคนทำ

**กันงานตกหล่น** ถ้าไม่มีผู้ใช้บทบาทนั้นเหลืออยู่เลยในระบบ (`orphanStage_`) ใบจะเข้าคิวของ
Super Admin แทน เพื่อไม่ให้ค้างโดยไม่มีใครเห็น

### คนตรวจกับคนอนุมัติต้องคนละคน

`effectiveApprover_(claim)` จะ**ไม่ยอมรับ** ค่า `approverEmail` ที่ตรงกับ `checkedBy` หรือ `createdBy`
คืนค่าว่างแทน แล้วปล่อยให้ใบวิ่งไปหาผู้ใช้บทบาท `Manager` ตามปกติ

จำเป็นเพราะใบเบิกยุคแรกถูกบันทึก `approverEmail` มาจากโปรไฟล์ตอนนั้น ซึ่งบางคนตั้งตัวเอง
เป็นทั้งผู้ตรวจและผู้อนุมัติ พอ Admin กดตรวจผ่าน ใบก็เด้งกลับเข้าคิวของ Admin คนเดิมให้อนุมัติต่อ
คนเดียวผ่านสองขั้น และ Manager ไม่เคยเห็นใบนั้นเลย

`canApproveClaim_` ก็กัน `checkedBy` ไม่ให้อนุมัติซ้ำด้วย ไม่ใช่แค่ซ่อนจากคิว
ส่วน `checkClaim` เขียน `approverEmail` ที่ผ่านการกรองแล้วกลับลงชีต ค่าค้างเก่าจึงถูกล้างเมื่อใบเดินผ่านขั้นตอนนี้
และไม่ส่งอีเมลแจ้งเตือนกลับหาตัวคนตรวจเอง

### Admin เห็นใบเบิกทุกใบทุกสถานะ

Admin มีหน้าที่**พิมพ์เอกสารหลัง Manager อนุมัติ** จึงต้องตามใบได้ตลอดสาย ไม่ใช่แค่ตอนที่ใบอยู่ในคิวตัวเอง
`listClaims` และ `getClaim` จึงเปิดให้ `isChecker` เห็นทุกใบ เท่ากับ `Finance` และ `Super Admin`
แท็บจึงเปลี่ยนชื่อเป็น **ใบเบิกทั้งหมด** และปุ่ม **พิมพ์ / PDF** ใช้ได้ทุกใบ
(`exportClaimPdf` ตรวจสิทธิ์ผ่าน `getClaim` อยู่แล้ว จึงเปิดตามกันเอง)

`Sale` ยังเห็นเฉพาะใบของตัวเองเหมือนเดิม

### แท็บรายการเปลี่ยนชื่อตามสิ่งที่คนนั้นเห็นจริง

| ใครเห็น | ชื่อแท็บ | เนื้อหา |
|---|---|---|
| `Super Admin` / `Finance` / `Admin` | **ใบเบิกทั้งหมด** | ทุกใบในระบบ มีช่อง "เฉพาะที่ฉันจัดทำ" ให้กรองเอง |
| `Sale` | **ใบเบิกของฉัน** | ใบของตัวเอง ซ่อนช่องกรองเพราะเซิร์ฟเวอร์กรองให้แล้ว |
| `Manager` | **ประวัติการอนุมัติ** | ใบที่ตัวเองอนุมัติไปแล้ว บวกใบที่รออนุมัติอยู่ |

`involvedInClaim_` เป็นตัวกำหนดว่าใครเห็นใบไหน โดยดูจากทุกช่องที่ผูกคนกับใบ
(`createdBy` `checkedBy` `approvedBy` `paidBy` `checkerEmail` `approverEmail`) บวกกับคิวปัจจุบัน
Manager จึงเปิดใบที่อนุมัติไปแล้วย้อนหลังได้ และพิมพ์ PDF ซ้ำได้

`switchView` จะไม่ย้ายไฮไลต์แท็บถ้าแท็บปลายทางถูกซ่อนอยู่ — Manager เปิดใบจากหน้าประวัติแล้ว
เนื้อหาจะแสดงในมุมมองแบบฟอร์ม (อ่านอย่างเดียว) โดยไฮไลต์ยังค้างที่ **ประวัติการอนุมัติ**
ไม่ใช่หายไปเฉย ๆ เพราะแท็บแบบฟอร์มถูกซ่อนสำหรับบทบาทนี้

**แจ้งเตือนตอนอนุมัติ** `notifyPrint_` ส่งอีเมลหา Admin ที่เป็นคนตรวจใบนั้น (`checkedBy`)
พร้อม PDF แนบ เมื่อ Manager กดอนุมัติ ถ้าใบไม่มี `checkedBy` จะส่งหาผู้ใช้บทบาท `Admin` ทุกคนแทน
ไม่ได้เพิ่มขั้นตอนใหม่ใน `STAGES` เพราะจะไปโผล่เป็นขั้นที่ 5 บนแถบความคืบหน้าโดยไม่มีอะไรมาปิดขั้นนั้น

### บทบาทที่ไม่ทำใบเบิก — `CFG.ROLES_NO_CLAIM`

```javascript
ROLES_NO_CLAIM: [ 'Manager' ],
```

บทบาทที่อยู่ในรายการนี้จะ**ไม่เห็นแท็บ แบบฟอร์ม และ ใบเบิกของฉัน** เลย
เหลือเฉพาะงานอนุมัติกับโปรไฟล์ ป้ายสถานะใบเบิกบนแถบบนก็ถูกซ่อนด้วย

**ไม่ได้ซ่อนแค่หน้าจอ** — `saveClaim` และ `submitForApproval` เรียก `requireClaimRight_()`
ซึ่งอ่านจาก `identity.canClaim` ถ้าบทบาทไม่มีสิทธิ์จะถูกปฏิเสธที่เซิร์ฟเวอร์
ต่อให้ยิงคำสั่งเข้ามาตรง ๆ ก็ไม่ผ่าน

**จะเปิดคืนเมื่อไหร่** แก้เป็น `ROLES_NO_CLAIM: []` แล้ว `clasp push` — ไม่ต้องแก้ที่อื่น
`Super Admin` ได้รับยกเว้นเสมอ ไม่ว่าจะตั้งค่าอย่างไร

> เคยลองใช้กฎ "เด้งไปหน้าคิวเฉพาะตอนมีงานค้าง" แล้วพบว่าใช้ไม่ได้ —
> หน้าแรกของคนคนเดียวกันเปลี่ยนไปมาแล้วแต่วัน และวันที่คิวว่าง Manager จะเข้ามาเจอ
> หน้ากรอกใบเบิกซึ่งไม่ใช่งานของเขา **หน้าแรกต้องเดาได้ว่าจะเจออะไร**

ผู้ที่มีหลายบทบาทยังกดแท็บ **แบบฟอร์ม** เพื่อทำใบเบิกของตัวเองได้ตามปกติ
ลิงก์จากอีเมลแจ้งเตือน (`?page=...&id=...`) ยังมาก่อนเสมอ

### หน้าอนุมัติของ Manager

หน้า **ตรวจสอบรายการ** ใช้ร่วมกับ Admin แต่สลับโหมดตามสิทธิ์ของคนที่เปิด

Manager (ขั้นรออนุมัติ) จะได้การ์ด **ข้อมูลสำหรับการอนุมัติ** เพิ่มขึ้นมาบนสุด:

- ยอดที่ขออนุมัติตัวใหญ่ พร้อมจำนวนรายการ
- ผลการตรวจของ Admin: ใครตรวจ ตรวจเมื่อไหร่ ผ่านกี่รายการ ติดปัญหากี่รายการ และความเห็นที่เขียนไว้
- ยอดแยกตามหมวดบัญชี (เห็นว่าเงินลงบัญชีไหนบ้าง)
- ค่าน้ำมัน Fleet Card แสดงเป็นข้อมูลประกอบ ไม่รวมในยอดอนุมัติ

ตารางรายการเปลี่ยนเป็น **ดูอย่างเดียว** — ปุ่มผลตรวจรายบรรทัดกดไม่ได้ (เห็นผลที่ Admin ทำไว้)
ปุ่มล่างเหลือ **ตีกลับให้แก้ไข** กับ **อนุมัติ** และช่องความเห็นเปลี่ยนหัวข้อเป็น *ความเห็นของผู้อนุมัติ*

### หน้าตรวจสอบของ Admin

- แสดงข้อมูลผู้จัดทำ ยอดรวม และรายละเอียดว่าเงินแต่ละบรรทัดลงช่องไหนบ้าง
- ปุ่มผลตรวจรายบรรทัด คลิกวน `ยังไม่ตรวจ → ✓ ผ่าน → ⚑ ติดปัญหา`
- ช่อง **หมายเหตุผู้ตรวจ** รายบรรทัด — เมื่อกดตีกลับ ระบบรวมหมายเหตุเหล่านี้เป็นเหตุผลให้อัตโนมัติ
- ติ๊ก **แก้ไขตัวเลขได้** เพื่อแก้จำนวนเงินให้ถูกต้องแทนการตีกลับ (เลขที่และสถานะคงเดิม)
- แถบความคืบหน้าบอกว่าตรวจไปกี่รายการ
- **กด "ตรวจสอบผ่าน" ไม่ได้ถ้ายังมีบรรทัดติดธง ⚑** — ต้องแก้ให้เรียบร้อยหรือตีกลับก่อน

ตั้งโฟลเดอร์ปลายทางได้ที่ `PDF_FOLDER_ID` ใน `Secrets.gs`

## โครงสร้างข้อมูล

**`Users`** — ทะเบียนผู้ใช้
คอลัมน์ 8 ตัวแรกเหมือน Tender ทุกประการ (`Email`, `FullName`, `Role`, `PasswordHash`,
`Salt`, `Active`, `CreatedAt`, `LastLogin`) แล้วต่อด้วยข้อมูลเฉพาะใบเบิก
(`EmployeeCode`, `Division`, `JobTitle`, `DefaultSupportDiv`, `CheckerEmail`, `ApproverEmail`, `Phone`, …)

**`Claims`** — 1 แถวต่อ 1 ใบเบิก เก็บหัวฟอร์ม ยอดรวม สถานะ และรอยเท้าของทุกขั้นอนุมัติ
(`submittedAt`, `checkedBy/At`, `approvedBy/At`, `rejectedBy/At/Stage/Reason`, `paidBy/At`)

**`ClaimItems`** — 1 แถวต่อ 1 รายการย่อย ตรงกับคอลัมน์ B–S ของ Excel
บวก `rowTotal` และผลตรวจของ Admin (`reviewFlag`, `reviewNote`)

**`ApprovalLog`** — บันทึกทุกการกระทำ (`Submit`, `Resubmit`, `Check`, `Approve`, `Reject`, `Pay`, `Edit`, `Delete`)
พร้อมผู้ทำ เวลา และความเห็น

**`Master`** — รายการสำหรับ dropdown (`employees`, `divisions`, `jobTitles`, `supportDivs`)
คอลัมน์ `supportDivs` คุมตัวเลือก **Support Div.** (BB / BP / TRC) เพิ่มแผนกได้โดยพิมพ์ต่อในคอลัมน์นี้

## การปรับแต่งที่พบบ่อย

| ต้องการ | แก้ที่ |
|---|---|
| เพิ่ม/ลดช่องค่าใช้จ่าย | `ITEM_FIELDS` ใน `Config.gs` (ทั้งฟอร์ม สรุป และ PDF ปรับตามเอง) |
| เปลี่ยนหมวดบัญชี / เลขบัญชี | `GROUPS` |
| เพิ่มแผนกใน Support Div. | คอลัมน์ `supportDivs` ในชีต `Master` หรือ `DEFAULT_MASTER` ใน `Config.gs` |
| เปลี่ยนตัวเลือกเริ่มต้นของ ฝ่าย / แผนก | `DEFAULT_MASTER.divisions` ใน `Config.gs` (ปัจจุบัน Sales Representative, Marketing) |
| เพิ่ม/ลดฟิลด์ตอนสมัคร | `REGISTER_FIELDS` + `PROFILE_COLUMN_MAP` ใน `Config.gs` |
| แก้/เพิ่มคำแปลบนหน้าจอ | `I18N` ที่หัวไฟล์ `JavaScript.html` (มี `th` และ `en`) |
| เปลี่ยนภาษาเริ่มต้น | ค่า `LANG` เริ่มต้นใน `JavaScript.html` (ค่าปัจจุบันคือ `th`) |
| เปลี่ยนชุดสี / โหมดมืด | ตัวแปร CSS ใน `:root` และ `[data-theme="dark"]` ของ `Stylesheet.html` |
| เพิ่มจำนวนบรรทัดสูงสุด | `CFG.MAX_ROWS` (ต้องขยายเลย์เอาต์ใน `FormSheet.gs` ตาม) |
| บังคับให้ผู้ดูแลอนุมัติผู้สมัคร | `CFG.AUTO_APPROVE_REGISTRATION = false` |
| ปิดอีเมลแจ้งเตือน | `CFG.NOTIFY_BY_EMAIL = false` |
| เปิดขั้นตอนจ่ายเงิน | `CFG.REQUIRE_PAYMENT_STEP = true` |
| ให้แก้ใบที่อนุมัติแล้วได้ | `CFG.LOCK_AFTER_SUBMIT = false` |

## ข้อจำกัดที่ควรทราบ

- แบบฟอร์มรองรับ **25 บรรทัดต่อใบ** ตามต้นฉบับ เกินกว่านั้นระบบจะให้แยกใบใหม่
- โควตาส่งอีเมลของ Apps Script: 100 ฉบับ/วัน (บัญชีทั่วไป) หรือ 1,500 ฉบับ/วัน (Workspace)
  — อีเมลแจ้งเตือนและลิงก์ลืมรหัสผ่านนับรวมในโควตานี้
- Apps Script ไม่มี bcrypt/argon2 ให้ใช้ — SHA-256 วนซ้ำ 5,000 รอบเป็นสิ่งที่ทำได้ดีที่สุด
  ในสภาพแวดล้อมนี้ (เท่ากับที่ Tender ใช้อยู่) เหมาะกับระบบภายในองค์กร
  ถ้าต้องรับข้อมูลอ่อนไหวกว่านี้ ควรย้ายไปใช้ผู้ให้บริการ auth จริง
- ชีตเป็นฐานข้อมูล จึงเหมาะกับปริมาณระดับหลักพันแถว ไม่ใช่หลักแสน
